# Tool-by-tool keyword fit audit and implementation plan

**Date:** 21 October 2026  
**Inputs:** current source definitions under `src/data/` and the 1,040-candidate inventory in [KEYWORD-RESEARCH-AND-SEO-PLAN.md](KEYWORD-RESEARCH-AND-SEO-PLAN.md).

## Audit finding

All 30 tool pages already have a dedicated H1, meta title, meta description, substantial explanatory sections, and FAQs. The core phrase is present in the page name/title/H1 and usually repeated naturally in the body. The `keywords` property in the source is used for the site’s internal tool search/card data; it is **not** a Google meta-keywords tag and should not be treated as a ranking field. There is room to add selected long-tail intent where it helps clarify a use case, but there is no SEO benefit to inserting all candidate phrases into every page.

The inventory is highly templated (for example, “for small business” or “how to use …” repeats across many tools). Treat those as prompts for SERP validation, not as proven search terms. This audit checks topical fit against actual page content; it does not claim search volume or difficulty.

## Site-wide implementation rules

1. Keep each existing tool URL as the canonical landing page for its one core intent. No new URL for every modifier or variant.
2. Where accurate, use one validated secondary phrase in the meta description or first explanatory section, and answer a real question in an existing FAQ. Do not expand titles merely to fit variants; current title length constraints are enforced by the build.
3. Add examples and related internal links only where they help the user. FAQs should answer real product/use questions, not serve as keyword containers.
4. Keep the source `keywords` field useful for internal search; it can include close synonyms, but it is not on-page SEO metadata.
5. Preserve product truth: privacy claims must distinguish in-browser processing from URL checks that may use the site proxy; tools must not promise rankings/indexing or platform behavior they cannot control.
6. After edits, rebuild and inspect rendered HTML. Then use Search Console query data before further keyword expansions.

## Category and homepage placements

- **Homepage:** keep focused on the complete suite and differentiators. Avoid trying to rank the homepage for every tool-level query.
- **SEO & Meta Tools:** reinforce tool selection by task (generate tags, preview snippets, validate page signals) and link directly to each relevant tool.
- **AI Search & Crawler Tools:** explain the difference between robots directives, AI crawler selection, and llms.txt; use careful, current language.
- **Content & Social Tools:** group link tracking, text analysis, social metadata and writing utilities by job to be done.
- **Web Utility Tools:** group developer utilities; make technical output limitations and privacy behavior clear.
- Add proposed guides from the keyword plan only after they are written as complete stand-alone answers. Guide links should point to the relevant tool, and tool pages should link back to guides where they help users.

## Implementation order

### First: validate what deserves a change

For each core topic, inspect live SERPs in target markets and note if results favor a generator, checker, tutorial, template, or reference. Use GSC once available to see actual query wording. Choose one primary and at most a few meaningful secondary intents per URL.

### Second: low-risk on-page improvements

Edit source data in `src/data/*.js`, not generated `dist/`. Update title/description only where it improves clarity and click appeal while staying within build limits; update intro/sections/FAQs only to add genuinely useful detail. Do not alter H1 solely to echo modifiers. Link related tools contextually.

### Third: inspect the result

Run the project build, confirm no title/description warnings, inspect generated HTML for each changed page, verify content is visible before JavaScript, and confirm canonicals/internal links. After deployment, annotate edits and compare GSC query/page CTR and impressions after adequate data accrues.

## Do not inject these phrases

- Repetitive modifiers like “no signup”, “for small business”, “for bloggers”, or “best free” where they do not describe a distinctive capability or user need.
- Every phrase in the 1,040-row backlog, or a list of variants stuffed into a section.
- Search-volume/difficulty claims, ranking guarantees, fixed snippet-length guarantees, or indexing promises without evidence.
- Keywords in hidden text, repeated FAQ questions, or separate doorway pages that only swap a few words.
