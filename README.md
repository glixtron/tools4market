# Tools4Market

Free, browser-based marketing, SEO, AI-search and web tools. **44 tools**, no signup, no limits. Text and image processing runs locally in the browser; optional public-page analysis sends the entered URL through our first-party fetch proxy.

Static site generated by a single Node script. No frameworks, no npm dependencies, no database, no API keys. Hosting cost: ₹0. Deployed to **Cloudflare Pages** — the static pages are the frontend, and two tiny serverless routes (`/api/fetch` and `/api/suggest`) are the backend: one lets the tools read a customer's live URL without CORS, the other drafts AI fixes through the Workers AI binding (also no API keys).

## Build & preview

```bash
node build.mjs        # or: npm run build   → regenerates dist/
npm run serve         # → node serve-dev.mjs (static + /api/fetch proxy on port 8090)
```

Then open <http://localhost:8090>.

`serve-dev.mjs` is a zero-dependency Node server that mirrors production: it serves `dist/` **and** implements the same `/api/fetch?url=…` proxy (and SSRF guard) as the Cloudflare Pages Function, so the "Analyze your own page" URL mode works locally exactly like it will after deploy. A plain static server (`python3 -m http.server`, `npx serve dist`) also works — the URL panel then degrades gracefully to its paste-HTML path.

> Keep port **8090** as the canonical dev URL (test harnesses and docs assume it). If it's busy: `PORT=8091 npm run serve`.

**Rules:**
- `dist/` is **generated — never hand-edit it**. Change files under `src/`, then rebuild.
- After any change to `src/`, run `node build.mjs` (see rules.md §6).

A clean build prints:

```
✔ Built 81 HTML pages (44 tools, 5 categories, 5 policy pages, 24 guides and blog hub) + sitemap.xml, robots.txt, 404.html, assets.
```

The build also warns if any page's `<title>` exceeds 60 characters or its meta description exceeds 158 — fix the data file rather than ignoring the warning.

## Adding a new tool

Two edits — one data definition, one runtime function — then rebuild. The build auto-lists the tool on the homepage, its category page, the related-tools sidebar and the sitemap.

### 1. Data definition (build-time)

Add an object to the matching category file in `src/data/` (`seo.js`, `ai-search.js`, `content.js`, `web.js` or `marketing.js`):

```js
{
  slug: 'word-counter',                 // URL becomes /tools/word-counter/
  name: 'Word Counter',
  cat: 'content',                        // must match a CATEGORIES id in src/data/index.js
  icon: '🔢',
  card: 'Count words, characters and reading time instantly.',
  keywords: 'word counter character count reading time',
  focus: 'word counter',                   // the ONE search phrase this page targets
  h1: 'Free Word Counter — No Signup, No Limits',           // pattern required by rules.md
  metaTitle: 'Free Word Counter — Words, Chars & Read Time', // ≤60 chars
  metaDesc: 'Count words, characters, sentences and…',       // ≤158 chars
  intro: 'One-line summary shown under the H1.',
  sections: [                            // 3–4 unique sections, hand-written
    { h: 'What it does', p: ['Paragraph one…', 'Paragraph two…'] },
    { h: 'How to use it', p: ['Steps…'] },
  ],
  faqs: [                                // 3–6 questions → FAQPage schema, auto-added
    { q: 'Is it free?', a: 'Yes — every tool on this site is free.' },
  ],
  html: `
${f.textarea('wc-text', 'Your text', 'Paste or type here…', 6)}
${outputArea('wc-out', 'Counts')}`,     // helpers: f.text/url/textarea/select/number/date/check, outputBlock, outputArea, note
},
```

Every user-facing string lives in these data files — never hardcode copy inside runtime files (rules.md §3).

**`focus` is mandatory.** It is the single search phrase the page targets, and the SEO audit enforces that it appears in the meta title, meta description, intro, at least one section heading and at least two FAQs — so every page has one clear keyword target instead of a keyword list. Run `npm run test:seo` after adding or editing a tool; it checks all pages (titles, descriptions, H1s, intros, keyword targeting, section depth, FAQ quality, structured data, internal linking, HTML hygiene and site-wide duplicates).

### 2. Runtime logic (client-side)

Register an init function in the matching `src/runtime/*.js` under the same slug:

```js
T['word-counter'] = function (root) {
  var out = $(root, 'wc-out');
  function update() {
    var text = $(root, 'wc-text').value;
    var words = text.trim() ? text.trim().split(/\s+/).length : 0;
    out.textContent = 'Words: ' + words;        // textContent only — never innerHTML for user data
  }
  root.addEventListener('input', update);
  update();                                     // always render initial state
};
```

**Conventions (rules.md §3):**
- Element IDs prefixed per tool (`wc-`, `mt-`, `og-`…) so pages never collide.
- Classic script, no ES modules — the site must also work opened from disk.
- All dynamic output via `textContent` / `createElement`.

**Optional — the "analyze your page" panel:** every tool page automatically gets an "Analyze your own page first" panel (URL box + paste-HTML fallback). It reads the live page and can pre-fill your tool's inputs and show a personalized fix list. To wire a new tool into it, add an `APPLY[slug]` entry in `src/runtime/inspect.js` (and a `tipFor` case) — the panel mounts itself; no markup needed. Tools that own a native URL box (like the two crawler/ranking tools) are listed in `SKIP_PANEL` there. All panel/audit copy lives in `src/data/inspect.js` and is injected at build time.

### 3. Rebuild and verify

```bash
node build.mjs
```

Confirm the build warns nothing, then test in a browser before declaring it done (rules.md §6): empty input, real input, weird characters, mobile width, copy button.

**Pre-ship checklist for every tool (rules.md §2):** working logic + edge cases · H1 pattern · title/description limits · ≥2 content sections · 3–5 FAQs with schema · copy button on every output · mobile + keyboard operable · listed on homepage + category + related sidebar · in sitemap (automatic).

## Testing & verification

The site itself has **zero dependencies**, so the test tooling is installed separately (never committed, never deployed):

```bash
npm i --no-save jsdom      # test-only
npm run build
npm test                   # tests/smoke.mjs — every tool page boots, responds, zero console errors
npm run test:seo           # tests/seo-audit.mjs — site-wide SEO definition audit (1 500+ checks)
npm run test:consent       # tests/consent-test.mjs — consent mode behaviour
npm run test:worker        # tests/worker-routing.mjs — http→https + canonical-host routing (no network)
npm run test:live          # tests/live-verify.mjs — checks the PUBLIC site (DNS, sitemap, every URL, backend, assets, Google tag on every page)
npm run indexnow           # scripts/indexnow.mjs — submit new/updated URLs to IndexNow (needs INDEXNOW_KEY)
npm run check:sources      # scripts/check-sources.mjs — every cited source URL still returns 2xx (network)
```

`npm test` boots all tool pages in a real DOM (jsdom): form controls and buttons are exercised, and the run fails on any console error, uncaught exception, missing tool registration or missing output. Browser file selection is not simulated by this smoke harness.

`npm run test:seo` audits the whole site against the SEO definition: every tool declares a `focus` target phrase that must appear in its title, description, intro, a heading and two FAQs; plus title/description/H1 length and uniqueness, 430–600-word sections, FAQ quality, structured-data completeness (WebApplication + FAQPage + BreadcrumbList + BlogPosting), internal linking, HTML hygiene, site-wide duplicate detection — **and a check that every built page carries exactly one Google tag with the consent default before it**.

`npm run test:worker` exercises `worker.js` directly with synthetic requests, so the redirect rules are tested before a deploy rather than only after one: `http://` on the apex or on `www` must reach `https://tools4market.online` in **one** hop with the path and query intact, an `X-Forwarded-Proto` header must not be able to skip the redirect, `https` must never redirect-loop, localhost is exempt so `npm run preview` still works, and `dist/_headers` must carry HSTS without `includeSubDomains`.

`npm run test:live` verifies what Googlebot actually sees: authoritative DNS, the sitemap index + children, **every URL in every sitemap** (200 + self-referencing canonical + indexable), `robots.txt`, the `/api/fetch` backend (including the SSRF guard), the Bing verification file, the AdSense loader + `ads.txt`, plain-http → https enforcement on both hosts, HSTS, and the Google tag on every published page. The last full run is recorded in [`launch-verification.md`](launch-verification.md) and [`qcreport.md`](qcreport.md).

`npm run check:sources` follows every URL in every guide's `links[]` and fails on a 4xx or 5xx. Redirects are classified rather than treated as one thing: a locale redirect (`?hl=fr`) or a trailing-slash change is reported and ignored, while a **moved** path means the document was relocated and the citation has to be re-pointed or dropped. Run it before publishing a content pack — a citation that 404s is worse than no citation. `--strict` also fails on moved links.

### Guides (`/blog/`)

Twenty-four how-to guides covering the queries our tools sit next to: robots.txt for search engines and AI crawlers, the website launch SEO checklist, how to block GPTBot, an llms.txt guide, appearing in ChatGPT search, checking whether AI crawlers can reach your site, noindex vs robots.txt, why a site is not indexed, UTM naming conventions, schema markup for AI search, a Screaming Frog alternative comparison, meta description length in 2026, internal linking, image SEO, Core Web Vitals in 2026, Open Graph image size, .htaccess 301 redirects, title tag length in 2026, URL slugs, rel=canonical, hreflang, XML sitemaps, testing structured data, and HTTP status codes. Each guide is a real page — `BlogPosting` + `FAQPage` + `BreadcrumbList` schema, author and reviewer, cited sources, and links into the tools it discusses. Articles live in `src/data/blog.js`; the build generates the hub, the article pages, the schema and `sitemap-blog.xml`. A guide can point at other guides through `relatedGuides[]`, which renders a **Read next** block — `relatedTools[]` is tool-slugs-only, and an unknown slug is dropped silently, so the SEO audit asserts that every guide carries at least three tool slugs and that every slug in both fields resolves to a real tool or guide. ### Analytics & cookies (Google Tag Manager + GA4 + Consent Mode v2)

Every page ships **one** Google tag per page, in the order Google's Consent Mode v2 documentation requires (the order is vital — consent defaults only work if they run first):

```html
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <script>
    window.dataLayer = window.dataLayer || [];
    function gtag(){dataLayer.push(arguments);}
    // 1. default consent state  (see below)
    gtag('consent', 'default', { ad_storage:'denied', ad_user_data:'denied',
      ad_personalization:'denied', analytics_storage:'denied', wait_for_update:500, region:[…EEA/UK/CH…] });
    gtag('consent', 'default', { …granted… });        // everywhere else
    gtag('set', 'url_passthrough', true);              // keep measurement without cookies
    gtag('set', 'ads_data_redaction', true);           // redact ad ids when ad_storage is denied
  </script>
  <!-- Google tag (gtag.js) -->
  <script async src="https://www.googletagmanager.com/gtag/js?id=G-6B4GGFC96K"></script>
  <script>gtag('js', new Date()); gtag('config', 'G-6B4GGFC96K', {anonymize_ip:true});</script>
  <!-- Google Tag Manager -->
  <script>…gtm.js?id='+i…  (GTM-P6P4FLGB)</script>
</head>
<body>
  <!-- Google Tag Manager (noscript) -->
  <noscript><iframe src="https://www.googletagmanager.com/ns.html?id=GTM-P6P4FLGB" …></iframe></noscript>
```

**Consent types (v2):** `ad_storage`, `ad_user_data`, `ad_personalization`, `analytics_storage`.

**Basic vs advanced consent mode** — switch with one env var:

| `CONSENT_MODE` | Behaviour |
|---|---|
| `basic` *(default)* | Denied in the EEA/UK/CH (29 countries), granted elsewhere — Google's recommended basic mode, so measurement is preserved where no banner is legally required |
| `advanced` | Denied for **every** visitor, everywhere — nothing is sent until someone accepts |

**How the choice flows:**
1. First visit → the inline script sets the default state (denied in the required regions, `wait_for_update: 500` so the banner can answer before tags fire). The cookie banner appears.
2. The visitor chooses → `gtag('consent','update', …)` fires **immediately, on the same page** (never on unload), and the choice is persisted in `localStorage` (`t4m_consent`).
3. Return visits → the inline script **restores the stored choice as the default before any tag loads**, so the correct state is set on subsequent page loads.
4. "Cookie settings" in the footer reopens the preferences; `window.T4M_CONSENT.get()/update()/granted()` is exposed for any custom UI.

**One thing to set up in your GTM container** (once, in the GTM UI): use Google's [consent mode template](https://developers.google.com/tag-platform/tag-manager/templates/consent-apis) (or create one with `setDefaultConsentState` / `updateConsentState`) and set the Consent Mode variables' default to **Denied**. Google specifically recommends the Tag Manager APIs over `gtag('consent','update', …)` inside a container — the site-level `gtag` calls above cover GA4, the template covers GTM's own tags.

> **Avoid double counting:** the site loads GA4 directly (`G-6B4GGFC96K`) *and* GTM. If your GTM container also contains a **Google Analytics / GA4 Configuration** tag, remove one of the two — otherwise every pageview is counted twice.

Verify with `npm run test:consent` (30 behavioural checks, incl. execution order, v2 types, region scoping, `wait_for_update`, passthrough, redaction, persistence/restore) and `npm run test:live` (Google tag + GTM + consent presence on the public site).

## Deploying to Cloudflare

### Path A — Workers (the current pipeline: GitHub → `npm run deploy`)

`wrangler.jsonc` is committed, so wrangler never runs its interactive setup wizard on the build server — the deploy is one command.

- **Build command:** `npm run build` · **Deploy command:** `npm run deploy` (which runs the build first, then `npx wrangler deploy` — so the deploy can never run without a fresh `dist/`)
- `wrangler.jsonc` sets: Worker name `tools4market`, entrypoint `worker.js`, static assets from `dist/` bound as `env.ASSETS`, `html_handling: auto-trailing-slash` (so `/tools/slug/` → `/tools/slug/index.html`), `not_found_handling: 404-page` (branded 404).
- **One Worker = frontend + backend:** `worker.js` serves the static site through the ASSETS binding and routes `GET /api/fetch?url=…` to the shared proxy handler in `functions/api/fetch.js` — same origin, so no CORS and no API keys.
- After the first deploy, attach the custom domain: Worker → **Settings → Domains & Routes → Add Custom Domain** → `tools4market.online` (the canonical host).
- **www → apex 301** (Workers Static Assets reject host-level rules in `_redirects` — error `100324`): do it at the **zone** level — Cloudflare → **Rules → Redirect Rules → Single redirect**:
  - If: `Hostname equals www.tools4market.online`
  - Then: **Dynamic redirect**, status `301`, target `concat("https://tools4market.online", http.request.uri.path)` (preserves the path), preserve query string.
  - Attach only `tools4market.online` to the Worker so the apex never redirects to itself (no loop).

### Path B — Cloudflare Pages (alternative)

1. Push this repository to GitHub (repo: `github.com/glixtron/tools4market`; or upload `dist/` directly via "Direct Upload").
2. Cloudflare Dashboard → **Workers & Pages → Create → Pages → Connect to Git** (or "Direct Upload") → select `glixtron/tools4market`.
3. Build settings:
   - **Framework preset:** None
   - **Build command:** `node build.mjs`
   - **Build output directory:** `dist`
4. Deploy. Cloudflare gives you a `*.pages.dev` URL — verify the homepage, a tool page and `robots.txt`/`sitemap.xml` there.
5. **Custom domain:** add `tools4market.online` under Custom domains (Cloudflare handles SSL automatically) and point the domain's nameservers at Cloudflare. Add a **Redirect Rule** `www.tools4market.online/*` → `https://tools4market.online/$1` (301) so the apex stays the canonical host.

On Pages, `functions/api/fetch.js` is deployed automatically as a Pages Function — no extra config, and the client calls it same-origin.

Any static host works the same way (Vercel, Netlify, GitHub Pages): build `node build.mjs`, publish `dist`.

### Cloudflare: frontend **and** backend in one project

Both layers ship from this single repo to one Cloudflare project — no second service to operate:

| Layer | What it is | Where it comes from | Runs on |
|---|---|---|---|
| **Frontend** | 81 static pages (HTML/CSS/JS, 44 tools and 24 guides) | `dist/` (built by `node build.mjs`) | Cloudflare static assets (global CDN) |
| **Backend** | `/api/fetch` live-URL proxy (SSRF-guarded) | `functions/api/fetch.js`, served by `worker.js` | The same Worker (serverless) — or a Pages Function on Path B |
| **Backend** | `/api/suggest` AI fix suggestions (consent-gated client) | `functions/api/suggest.js`, served by `worker.js` | The same Worker + the `AI` (Workers AI) binding — no API key anywhere |

Because the proxies live on the same host as the pages, the client can call `/api/fetch?url=…` and `POST /api/suggest` **without CORS** and without any API key in the browser. The same-origin setup also means one SSL certificate, one cache policy and one deployment to reason about.

**Private repo note:** the repo is private, so the Cloudflare Git integration must be granted access to it — in the Pages project → *Settings → Builds & deployments → Connect to Git*, or on GitHub → *Settings → Installed Apps → Cloudflare Pages → Configure → select `tools4market`*. A private repo that the App cannot see simply won't appear in Cloudflare's repo picker.

**If you later want a separate backend domain** (e.g. `api.tools4market.online`): `functions/api/fetch.js` is plain Workers-style code, so it can be deployed as a standalone Worker (`wrangler deploy`) with `Access-Control-Allow-Origin: https://www.tools4market.online`, and the client would call `https://api.tools4market.online/?url=…`. The current same-origin setup is simpler and free — treat the Worker split as a scale step, not a launch requirement.

### The `/api/fetch` proxy (live URL checks)

`functions/api/fetch.js` is a **Cloudflare Pages Function** — it deploys automatically with the site (no extra config, free tier 100k req/day, no API keys in the browser). It lets applicable tools read an arbitrary public page despite CORS, which powers the **"Analyze your own page first"** panel plus the **Web Crawler Audit** and **SEO Score Checker** tools.

- **On Cloudflare Pages:** the proxy is live automatically → paste any URL and the tool reads the real page.
- **On another static host / `file://` preview:** the endpoint 404s, so URL mode falls back to a direct browser fetch (works for CORS-open sites) and then to **paste-HTML**. Pasted markup is analyzed in-browser; public URL mode requests the entered page from the first-party proxy on the supported host.

If you deploy to a non-Cloudflare host and want live URL checks, port `functions/api/fetch.js` to that host's equivalent serverless function (Vercel/Netlify functions) — it is one of only two backend files in the project.

### The `/api/suggest` route (AI fix suggestions)

`functions/api/suggest.js` powers the **"Suggest a fix with AI"** button in the analysis panel: when a tool flags a fixable issue (missing/short meta description, weak title, missing social copy), it POSTs a compact snapshot — URL, title, H1, description and up to ~700 characters of opening text, **never the raw page** — and the route drafts replacement copy with **Cloudflare Workers AI** (`env.AI`, declared as the `AI` binding in `wrangler.jsonc`).

- **No API key exists at all:** the model runs behind a Worker binding on your Cloudflare account (Workers AI includes a daily free neuron allowance). `AI_MODEL` (optional Worker var) overrides the default `@cf/meta/llama-3.1-8b-instruct-fp8`.
- **Same-origin + consent-gated:** the route rejects cross-origin POSTs (`Origin` must match), and the browser only offers the button after the visitor accepts analytics consent (privacy policy §1 documents the data sent). Every response is labelled a draft to review — never a ranking promise.
- **Graceful degradation:** if the binding or model is unavailable, the route answers `{ ok:false, reason }` (503/502) and the client keeps its deterministic "Draft from this page" fallback plus the always-on gap list — the feature never breaks the tool.

### The site URL (already set for the live domain)

`SITE.url` in `build.mjs` is the canonical origin — every canonical tag, Open Graph URL, JSON-LD `url` field, sitemap entry and the `robots.txt` sitemap line is derived from it:


## Monetization: AdSense (connected)

**Publisher id: `ca-pub-1509697031230558`** — wired into the build, no manual editing required.

| Piece | Where it comes from | Status |
|---|---|---|
| Loader (`adsbygoogle.js?client=ca-pub-1509697031230558`) | every page `<head>`, async + `crossorigin="anonymous"` | ✅ live — this is what AdSense's site-ownership check looks for |
| `ads.txt` | generated at the domain root by the build | ✅ live (`google.com, pub-1509697031230558, DIRECT, f08c47fec0942fa0`) |
| Preconnect | `pagead2.googlesyndication.com` | ✅ live |
| Ad slots | three reserved `.ad-slot` containers per tool page (top banner, below content, desktop sidebar) | ✅ reserved height — no CLS when ads switch on |
| Real ad units | `AD_SLOT_TOP` / `AD_SLOT_CONTENT` / `AD_SLOT_SIDEBAR` env vars | ⬜ set the ad-unit ids from the AdSense console to switch them on |
| Privacy disclosure | `src/data/policy.js` — publisher id + "limited, non-personalised ads when consent is denied" | ✅ live |

**Consent-aware by design:** the loader is present in the HTML (required for verification), but Google's Consent Mode v2 state decides what actually happens — in the EEA/UK/Switzerland `ad_storage` is `denied` until the visitor accepts, so Google serves **limited, non-personalised ads** and sets no ad cookies. The banner's **Ads** toggle controls it.

**To switch on real ads:**
1. AdSense console → *Ad units* → create three display units (top banner, below content, sidebar) and copy their ids.
2. Cloudflare → Worker → *Settings → Variables and Secrets* → add `AD_SLOT_TOP`, `AD_SLOT_CONTENT`, `AD_SLOT_SIDEBAR` → redeploy. Each slot then renders a real `<ins class="adsbygoogle">` unit; until then the reserved placeholder stays (no broken units, no layout shift). The value must be the numeric `data-ad-slot` id (6+ digits); `ca-pub-<digits>:<digits>` is also accepted. Anything else is ignored by design, and the build now prints a `⚠ AdSense: … not numeric and ignored` line naming the variable — a malformed id otherwise ships a page that looks finished and earns nothing. `ℹ AdSense loader on, 0 ad units` means the placeholders are still in place.
3. AdSense console → tick *"I've placed the code"* → **Request review**.

**Rules:** nothing may ever sit inside the tool interaction area (rules.md §5) — the reserved slots are outside it by construction.
